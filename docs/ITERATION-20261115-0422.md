## 1. 错误列表与重载的零打扰根因（边界 1、2）

### 根因

- `browser_reload_extension` 的完成证据曾依赖 UI Automation 读取 `chrome://extensions` 面板；该路径需要一个**可见 Chrome 窗口**，且打开页签本身会在浏览器内切换前台 tab（OS 前台未夺走，但违反「零打扰」）。
- Chrome 无可见窗口时只能返回 `no_chrome_window`，调用方把「无法观察」误读成「状态未知」，于是反复重载——正是用户实测中的重复动作来源。

### 修复

- 新增 `src/extension-error-journal.js`：读取 `.local/logs/audit.jsonl`（含轮转 `audit.1.jsonl`）中 `tool:"extension-error"` 行，按 `eventId` 去重（新者胜）、按 `hostId` 过滤、按 `windowHours`/`since` 截窗，返回 `basis:"bridge-journal"`、`panelInspected:false`、`state:"errors_present"|"none_recorded"`、`categories`、`errorEntryNames`；**不返回原始 detail**。`none_recorded` 明确是「无证据」而非「面板为空」。
- `src/server.js` 重载路径：`chrome.runtime.reload()` 成功后先读日志（`since`=本次重载开始时间），**默认不打开任何页面**；`errorList.status:"not_attempted"`、`foregroundTaken:false`。只有显式 `clearErrors:true` 才后台（`active:false`）打开面板并用 UIA 清理；清理失败才 `partial:true`，未请求清理的重载一律完整。日志证据在清理失败时原样保留，不被覆盖。
- `browser_extension_errors` 默认也改走日志；`includePanel:true` 才附加 UIA 面板判定，且面板不可达时保留日志判定（`basis:"bridge-journal+chrome-panel"`），不再塌缩成裸 `unknown`。

## 2. 重复抑制指纹补齐修订信号（边界 3）

- 页内 `extension/page.js` 用 MutationObserver 维护 `globalThis.__aibRevision`，跨多次 `chrome.scripting.executeScript` 保持单调；`pageFingerprint` 返回 `revision`，但**修订号不进入 digest**。
- `extension/receipt.js`：`changed = digest 变化 || toggled || revision 变化`；同长度文本替换因此可被证明为变化。重复键仍为 `name|tabId|digest|args-hash`，所以「同一动作对未变页面重试」依旧被抑制（`DUPLICATE_WINDOW_MS=8000`），而不会因为一次无关变化被当作新动作放行。
- 回归：`test/action-receipt.test.js` 断言修订 3→4、digest 相同 ⇒ `changed:true`、`duplicateKey` 不变；不可用修订时说明文字包含「same-length text changes could not be ruled out」，且明确「不是动作失败的证据」。

## 3. 进程与 MCP 生命周期治理（边界 4 的根因层）

- **adapter 注册表**（0.41.0 已建，0.42.2 沿用）：`.local/mcp-adapters/<pid>.json`，15s 心跳，stale 判定 45s；`node src/cli.js adapters` 只读清单，`liveness:"not_checked"`；`--prune` 只按年龄删文件，不发信号。
- **双因子父进程守卫** `src/mcp-parent-guard.js`：先探测父进程**名称**，可读且不是 shell/launcher（`bash/sh/cmd/conhost/pwsh/powershell/node/npx/npm/终端`）才武装；武装后每 30s 检查存活，父进程消失则 adapter 自行退出。名称不可读**连续 3 次**才解除武装——一次慢查询不会废掉整场守卫。
- 实测：本机 `tasklist.exe /FI` 超过 **8s**（5s 超时直接让所有父名为 `null`）；改为优先 `pwsh`/`powershell` 的 `Get-Process`（约 **0.75s**），`tasklist` 仅作末位兜底。名称统一小写并补 `.exe`，`node` 与 `node.exe` 同规则。
- `node src/cli.js processes`：本项目唯一清单（service pid 文件、watchdog pid 文件、全部 adapter），逐项 `alive`/`parentAlive`/`parentName`/`parentIsShell`/`orphanedCandidate`；`action:"report-only"`，pid 文件只当「声明」，**不发信号、不杀进程**；探测并行执行。
- `scripts/watch-service.ps1` 现在写 `.local/watchdog.pid`，使看门狗也能被同一清单认领。
- 残余边界：父进程本身是 shell/launcher 且已退出的 wrapper 场景，无法证明真实客户端，守卫按设计不武装；注册表仍能看见它。此项需要长期真实边界测试，不拍脑袋上线。

## 4. 多 agent 优先级与超时保护（边界 5）

- **读快车道**（`src/server.js:164-186`、`src/host-registry.js:297-324`）：
  - 每宿主最多 **2 个并发只读任务**（`MAX_READS_PER_HOST`），必须在**不同 tab**；
  - 写任务遇到该宿主有读在飞时**等待读排空**；读任务遇到写忙时也可并行（不同 tab）；
  - 同 tab 严格互斥（`busyTabKeys`，键按 `hostId:tabId` 作用域，因为每个浏览器都有 tab 7）；
  - 跨宿主完全独立——某个 Chrome 的慢读不会阻塞另一个浏览器。
- **优先级**：agent 策略 `queuePriority` 被夹在 **-100..100**；与等待时间 `aging`（1/秒、上限 100）和切换公平奖励（+15）共同决定顺序。短程任务用负值即可进入真快车道；长程/批量任务不会饿死（aging 会持续追赶，测试覆盖 `-50/40/夹取/aging 救援`）。
- **超时语义**：写任务超时按既有契约进入 `uncertain`，**不自动重放**；读任务超时只结束该读，不占用写通道。任务在服务队列中由服务持有，接入 agent 端超时不会把任务「撤回」——重连后用 `commandId` 取回记录结果，或重新观察页面。
- 回归：`test/multi-host.test.js` 纯逻辑（并行/上限/互斥/优先级/aging）+ 实时（长写不扣住短读、写等读、只在同宿主生效），`test/route-tool-e2e.test.js` 同步调整。

## 5. REA 与跨设备运行时（边界 6）

### 证据

- 本机 Qoder 配置的 REA 是 **Node MCP server**：`rea-agents@6.4.0`，MIT，`engines: ^22.19 || ^24.11 || >=26`；依赖 `playwright-core 1.58.2`、`parse5`、`@babel/parser`；提供 **170 个工具**（`inspect_web_page`、`analyze_web_bundle`、`recover_javascript_sources`、`inspect_web_event_listeners`、`observe_web_execution`、Electron targets 等）。
- 扩展层是 MV3，只能 JS，且页面函数必须可被 `chrome.scripting.executeScript({func})` 序列化——**任何 Python/Rust/Go/C++ 库都进不了扩展包**。

### 决策

- **不内嵌 Python/Rust/Go/C++，不内嵌 REA**。REA 作为**可选 peer** 由宿主侧 MCP 配置接入（本机已如此），与桥互补：桥负责真实 Chrome 的受控操作，REA 负责离线 bundle/JS 逆向；两者不共享登录态，不互相替代。
- 跨设备「开箱即用」改为**预检 + 明确降级**：新增 `node src/cli.js runtime`（schema `ai-browser-bridge-runtime-v1`）报告 Node ≥22（唯一必需）与可选 `npm/pwsh/powershell/python/go/rustc/rea` 的存在与版本；缺失只作为建议，不影响桥启动。`.cmd`/`.bat` shim 只报告存在、不执行。
- 本机实测：Node 27.0.0-alpha（满足 ≥22）、npm/pwsh 7.6.10/powershell/Python 3.13.9/Go 1.27.4/rustc 1.99.1/rea 全部存在，`recommendations:[]`。

## 6. 常驻形态决策（边界 7）

**保持并强化既有形态：按登录用户的常驻服务 + 看门狗 + 每客户端 stdio adapter + 扩展。**

- **不做 Windows 服务**：Session 0 与交互桌面隔离，UIA/`windows_control`/截图/窗口绑定都依赖当前用户会话；服务化会直接砍掉已交付能力。
- **不新增常驻进程**：当前常驻只有 `src/server.js`（127.0.0.1:19387，单实例锁）与 `scripts/watch-service.ps1`；adapter 是 MCP 协议要求（每个客户端一个），已由 EOF/EPIPE 清理 + 父进程守卫 + 注册表清单三层管理。
- **「更利于实战驻留」的落点是治理而非新程序**：`adapters`、`processes`、`runtime`、`doctor`、`heartbeat`、`usage` 六个入口覆盖「谁在跑、归谁、健康否、用了什么」。看门狗只在「`/status` 不通且端口空闲」时拉起，不做名字杀进程。
- 登录自启继续用既有 Startup/计划任务脚本；升级走 `build_restart`（仅空闲时）+ 按 `hostId` 重载扩展，均有验证回执。
