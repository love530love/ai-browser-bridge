## 1. 18:04 退出的证据链复原（边界 1）

### 可复原的事实

- 心跳 incident `55831f65` 记录了对 `build_stale` 的处理，actionId
  `06848c8f-59e7-40c9-88cf-6a992435f422`，方式 SIGTERM，目标 pid **203752**。
- 同一时段的冷却状态与该次动作一致；看门狗随后在 **18:04:37** 进入 `starting-service`，
  于 **18:04:53** 恢复 `connected`。
- `executeRemediation` 的 `build_restart` 分支确实向该 pid 派发了 SIGTERM；当前源码即由看门狗拉起。

### 根因

不是「谁杀了进程」发生了歧义，而是**体系没有留证的通道**：
动作发生在内存里，信号发出后旧进程没有任何持久化遗言；下一个进程启动时也不读取上一次运行的
结局。于是每次升级和每次异常退出在账本上都长得一样——「未取证」。

### 永久修复

`src/service-lifecycle.js` 新增 append-only JSONL 账本
（`.local/service-lifecycle.jsonl`，2MB 轮转），事件包括：

| 事件 | 写入者 | 含义 |
|---|---|---|
| `service_started` | `src/server.js` 主模块 | pid/ppid/buildId/version/port + `previousExit` 分类 |
| `shutdown_requested` | 信号处理器 | 收到 SIGINT/SIGTERM，准备优雅关闭 |
| `service_exited` | `process.once('exit')` | 退出码、原因、uptime、startId |
| `service_fatal` | `uncaughtException` | 未捕获异常 |
| `restart_intent` | 心跳 `build_restart` | **信号前**声明：intentId(=actionId)/pid/方法/原因/运行与磁盘 buildId |
| `restart_intent_cancelled` | 心跳派发失败/异常 | 意图未执行，防止被误判为计划重启 |

启动分类（`classifyRun`）：

| 上次运行状态 | 分类 |
|---|---|
| 无账本 | `first_start` |
| 同一 pid 的未取消意图先于退出 | `planned_restart` |
| 非零退出码或 fatal | `crash` |
| SIGINT/SIGTERM 且无意图 | `signal_shutdown_unattributed` |
| 退出码 0 且无意图 | `clean_exit_unattributed` |
| 有后继启动但无退出记录 | `unrecorded_exit` |
| 无后继启动 | `running` |

- `/status` 的 `queue.startup.previousExit` 暴露分类结果；`node src/cli.js service-history
  [--limit N]` 回放账本；`node src/cli.js processes` 附带 `lifecycle` 摘要。
- 心跳新增 `service_exit_unattributed` 规则：`crash` / `unrecorded_exit` /
  `signal_shutdown_unattributed` 且发生在 24h 窗口内 → warn，**report-only**，不自动重启。

### 为什么这算「永久」

- 计划内重启从现在起必须留下与 actionId 对齐的意图，否则下一次启动就会把它报告为未归因退出；
- 崩溃/未记录退出不再依赖人是否记得翻 incident；
- 不可归因的 SIGTERM 只陈述「没有意图」，不猜发送者——账本记录证据，不做归责。

## 2. wrapper-shell 守卫（边界 2）

### 根因

旧实现只探测**直接父进程**：名字可读且不在 shell/launcher 名单内才武装。wrapper 场景
（cmd/pwsh/bash/npx 等启动器）天然不满足，守卫永久 passive，adapter 失去父进程死亡感知。

### 修复

- `probeProcessChain` 沿 `Get-Process.Parent`（PowerShell 7）向上取链，Windows PowerShell
  5.1 回退 `Get-CimInstance Win32_Process`；本机 CIM 实测 >10s 超时，因此 pwsh 为主路径。
- `selectAncestorAnchor` 跳过 shell/launcher 与会话根（qoder、code、explorer 等），
  锚定第一个稳定祖先，记录 `{pid,name,created,ppid}`；`created` 必须以本机时区可解析为前提。
- 每个 tick 检查锚点存活；周期性重读创建时间识别 pid 复用：
  - 锚点消失 → `anchor_process_gone`（可安全清孤儿）；
  - 创建时间变化 → `anchor_identity_replaced`；
  - 连续 3 次身份不可读 → passive `anchor_identity_unverifiable`；
  - 链不可读 / 无稳定祖先 → passive `process_chain_unavailable` / `no_stable_ancestor`。
- `guard.snapshot()` 暴露 `mode/anchor/chain/reason/counters`，adapter 注册表与
  `node src/cli.js processes` 均可见；passive 模式的记录不会被 `orphanedCandidate` 误标。

### 本机实测

`bash.exe ×3 → qoder.exe`，锚点 pid 132968，完整探测 **825ms**。

## 3. 面板声明语义（边界 3）

`src/extension-error-claims.js` 的 `buildErrorClaims({journalState, panelState})` 返回：

- `journal`: `errors_present` | `no_recorded_events`
- `panel`: `errors_present` | `clean` | `not_inspected` | `unknown`
- `overall` / `cleanClaim`：
  - 面板有错误 → `errors_present`（主导）
  - 日志有错误 → `errors_present` / `journal_errors_panel_clean` / `journal_errors_panel_unknown`
  - 面板干净但日志有错误 → 不干净（`journal_errors_panel_clean`，`cleanClaim:false`）
  - 仅查日志（`panel:'not_inspected'`）→ `unknown`，`cleanClaim:false`
  - 只有「面板读取为空 **且** 日志无错误」→ `clean`，`cleanClaim:true`

工具输出同时带 `note`，直接写明「`none_recorded` 是无证据，不是面板已清空」。

## 5. 已知边界

- 账本只覆盖「本服务自己记录到的」退出；账本被外部删除后首次启动记为 `first_start`，不追溯。
- `signal_shutdown_unattributed` 不指认发送者；它是证据分类，不是归责。
- 祖先链依赖 PowerShell；不可用时守卫 passive，注册表可见性仍是最终依据。
