# 0.2.1 现场诊断与升级

2026-09-28。检查时日常 Chrome 仍连接旧版 0.2.0，WorkBuddy 正在使用；本次不重启现有服务，不操作其任务页。WorkBuddy mcp-apps-diag.log 未检索到对应工具调用明细，不能凭桥接日志确定客户端身份。

实际证据：近期读取、点击、截图均有成功记录；出现连续 browser_fill 失败，重新 browser_read 后 browser_fill 成功。旧日志未保存错误分类，无法确定这些失败是引用失效、只读字段还是其他原因；不能宣称已复现并修复该现场失败。历史验收中导航后读取曾多次失败。

已完成：
- browser_read 返回普通输入框/文本域/选择框的当前值（上限2000字符）、只读状态、勾选状态与最多100个选项。密码、文件、隐藏字段和 data-ai-private 继续排除；正文不写入审计日志。
- browser_fill 返回 valueMatches，核实立即 DOM 值是否与输入相同。它不是服务端保存或业务成功证明。
- MCP browser_read 遇明确导航/页面切换错误时最多重试6次、每次250毫秒；输入点击等写动作绝不自动重试。HTTP/CLI直接调用不自动套用此恢复。
- 服务审计新增固定错误类别，不记录原始错误、URL、网页正文和输入值。

验证：13项单元/服务测试、24项独立Chromium检查通过，增加输入值回读与下拉选项断言，继续验证密码和隐藏内容排除。日常Chrome的0.2.1尚未验收。

待完善：不同客户端读取同页仍会互相刷新元素ref；外部多步任务没有专属租约；复杂iframe/Shadow DOM/富文本支持仍不完整。暂停后不要盲目重复写入；必须先读取确认。不要让两个Agent并行修改同一页。

上线：WorkBuddy任务结束后运行 upgrade.ps1，再在chrome://extensions重新加载自主浏览器并连接，然后重载WorkBuddy的MCP连接。此过程保留配对，不需要配置模型。服务、扩展、MCP分别更新后才算全部启用。当前交付为已验证待切换版本，不把源码更新当成运行中版本已更新。
